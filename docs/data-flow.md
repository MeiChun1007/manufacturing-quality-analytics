# Data Flow

This document follows a production entry from the operator's form to the reports.

## End-to-end flow

```mermaid
flowchart LR
    A["Operator signs in"] --> B["Opens the data entry form"]
    B --> C["Fills production information"]
    C --> D["Adds one or more NC lines"]
    D --> E["Optionally attaches NC photos"]
    E --> F["Submits"]
    F --> G{"Server-side<br/>validation"}
    G -- "fails" --> H["Error message,<br/>nothing saved"]
    H --> C
    G -- "passes" --> I[("Save entry, NC lines,<br/>photo records")]
    I --> J["Internal Joomla reports"]
    I --> K["BI dashboard<br/>after refresh"]
    J --> L["Supervisors review"]
    K --> L
    L --> M["Investigate and<br/>take corrective action"]
```

## Step by step

### 1. Sign in
The operator signs in with a personal Joomla account. The system uses this account as the identity
of the person who entered the record.

### 2. Production information
| Field | Source |
|-------|--------|
| Reference number | Generated by the system: `IR` + `yymmdd` + record number |
| Created by, date, week | Filled automatically from the account and the current time (ISO week) |
| Operator | Operator account chosen or derived on the server |
| Part (component) | Dropdown from `product_components` |
| Model | Dropdown from `product_catalogs`, filtered by the chosen component |
| Vendor | Dropdown from the vendor accounts the user may see |
| Lot | Vendor and vendor-remark combination (`vendor_details`) |
| Total | Total quantity sorted/produced for the entry |
| Remark | Normal or Re-sort. A re-sort entry also records which NC type is being re-sorted |
| Work order no. | Optional free text |

### 3. NC lines
For each defect found, the operator adds a row with an NC category/type from the master data and the
quantity. One entry can have many NC rows. The system stores `nc_percentage` as
`nc_quantity ÷ total × 100`. NC photos can be attached to each NC row.

### 4. Validation
When the form is submitted, the server checks the data before saving anything. The rules are listed in
[technical-documentation.md](technical-documentation.md#validation-rules). If a check fails, the
operator sees a message and nothing is stored.

### 5. Storage
The data is saved in this order, so the links between tables are valid:

```mermaid
sequenceDiagram
    participant Op as Operator
    participant Web as Joomla (com_data)
    participant DB as MariaDB
    participant FS as File storage

    Op->>Web: Submit form (+ submission token)
    Web->>Web: Check token, required fields, quantities
    alt validation fails
        Web-->>Op: Show errors, nothing saved
    else validation passes
        Web->>DB: INSERT data_entry
        DB-->>Web: new entry id
        Web->>DB: INSERT data_entry_nc (one row per NC line)
        DB-->>Web: NC ids
        opt photos attached
            Web->>FS: Save image files
            Web->>DB: INSERT data_entry_nc_images (name, path)
        end
        Web-->>Op: Confirmation
    end
```

### 7. Review and action
Supervisors use the reports to find high-NC models, vendors, operators or NC types, and then investigate
the cause and track the corrective action.

## Data lifecycle

| State | Meaning |
|-------|---------|
| Active (`state = 1`) | Counted in reports |
| Trashed (`state = -2`) | Hidden from the normal lists and excluded from reports, but kept in the database |

Entries are soft-deleted so that a mistake can be recovered and the history is not lost.

## Integrations

External systems can read and write data through the REST API, authenticated with an API token.
The same validation rules apply, so API clients cannot create records the form would reject.
